본문의 코드 링크는 평가 근거 커밋에 고정했다. 제출 문서의 파일별 버전과 다운로드 경로는 산출물 저장소의 목록에서 확인한다. 두 저장소의 역할을 분리하며, 산출물 저장소를 Jetson 실행 원본으로 사용하지 않는다.

1. 프로젝트 한눈에 보기

조립 공정에서는 제품이 검사 위치에 도착했을 때 필수 부품이 모두 장착되어 있는지 빠르게 확인하고, 판정 결과와 근거를 추적 가능하게 남기는 것이 중요합니다.

이 프로젝트는 엔진 모형을 대상으로 다음 흐름을 실제 장비에 연결했습니다.

핵심 설계는 클라우드가 아니라 현장의 Jetson에서 촬영·추론·판정·저장을 수행하는 것입니다. 노트북은 개발·조회용이며, 이미 기동된 검사 서비스의 필수 실행 장치는 아닙니다.

검출 결과를 곧바로 PLC에 보내지 않습니다. 기본 결과와 원본, 통합 최종판정의 저장을 연결하고 같은 요청의 저장 완료를 확인한 뒤 Result·Done을 전달합니다. 웹 화면은 저장된 검사 이력을 조회하는 경로이며, 화면 조회가 PLC 전달의 선행 조건은 아닙니다. 저장·게시의 코드 연결은 7절과 06 DB 설명서 5쪽에서 확인할 수 있습니다.

3. 검사 대상과 판정 기준

M1 — 필수 부품 검출

운영 클래스는 다음 3개입니다.

  • gray_pipe — 좌/우 파이프 두 자리를 같은 클래스로 검출
  • exhaust_top
  • symbol_module

정상 모형에서는 gray_pipe 2개, exhaust_top 1개, symbol_module 1개가 기대됩니다.

M2 — 엔진 전체 검출

  • product_envelope 1개
  • 엔진 전체 영역을 검출해 검사 대상의 위치와 Pose 처리에 사용

최종 판정 정책

현재 최종 판정은 필수 부품 존재·결품을 기준으로 합니다.

  • PASS — 필요한 부품이 3프레임에서 일관되게 존재
  • FAIL — 필요한 부품의 결품이 3프레임에서 일관되게 확인
  • REVIEW — 자세·품질·가시성·프레임 일치 등으로 자동 확정이 어려움
  • ERROR — 카메라·프로그램·저장 등 시스템 오류

오조립 분류 M3~M6는 참고 정보로 저장·표시하지만 현재 최종 PASS/FAIL에는 반영하지 않습니다.

5. PT → ONNX → TensorRT 운영 모델 연결

현재 운영 모델은 학습 가중치부터 운영 plan까지 SHA-256으로 연결했습니다.

모델 PT ONNX 운영 TensorRT
M1 42db1830...bf5259 433b16fd...9c296 743ce54b...bf2d6c
M2 cf117def...0f7755 5cb024bb...ca830 c82f2658...cebf83

운영 TensorRT는 단순 파일 확장자 변경이 아니라, manifest에 고정된 입력·출력 계약과 전처리·후처리를 사용합니다. M1은 FP16 + head FP32, M2는 FP16 + backbone FP32이며 입출력은 float32인 혼합정밀도 구성입니다. 위 표의 축약값은 파일 식별용이고, 전체 SHA-256과 export·build 조건은 03 모델 평가서 및 07 Jetson 실행·변환 절차서에 제시했습니다.

  • 입력: batch 1, 640×640
  • letterbox + padding 114
  • BGR → RGB
  • /255
  • class-aware NMS
  • 원본 좌표 복원
  • native TensorRT execute_async_v3

실행 코드는 backend를 명시적으로 선택하며, 운영 TensorRT 실패 시 조용히 PyTorch로 fallback하지 않습니다.

7. PLC 연계와 저장 완료 확인

실물 통합 구성은 OMRON PLC와 OpENer cyclic I/O를 사용합니다. 기본 검사 결과와 통합 최종판정을 저장한 뒤, 같은 요청의 완료 여부를 확인하여 PLC에 게시합니다.

PLC Inspection_Request 수락
    ↓
요청에 귀속된 새 유효 프레임 확보·M2/Pose/M1 검사
    ↓
3프레임 기본 판정 및 원본·표시 이미지 저장
    ↓
오조립 참고 분석과 통합 최종판정 저장
    ↓
동일 요청의 저장 성공·완료 응답 확인
    ↓
PLC Result 게시
    ↓
후속 cyclic update에서 Done
    ↓
PLC 요청 LOW 복귀·운전 조건에 따른 다음 사이클

저장과 PLC 게시를 연결하는 코드

standalone.py의 _commit_and_publish()는 같은 요청에 속한 완료 기록과 storage_success를 확인합니다. OPENER_CYCLIC 경로에서는 submit_final()로 저장을 요청하고, _poll_final_commit()에서 완료 응답·요청 문맥을 검사한 뒤 _publish_committed()를 호출합니다. 06 DB 설명서 5쪽과 07 Jetson 실행·변환 절차서가 이 순서를 설명합니다.

최종 판정 PLC Result 의미
PASS false / 0 OK
FAIL true / 1 NG — 결품 등 판정 사유를 원장에 보존
REVIEW / ERROR true / 1 NG — 재확인·시스템 오류의 원판정과 원인을 별도로 보존

이 표는 같은 요청의 저장·완료 조건을 충족하여 결과를 게시하는 경로의 매핑입니다. 저장 실패나 유효 요청 부재 시에도 일반 완료 사이클과 동일하게 Result·Done을 보낸다는 의미는 아닙니다.

저장된 PLC 프로그램은 Done과 Result에 따라 정상·결품 기억 및 LED를 연결하고, 운전 조건에서 정상·NG 모두 재이송하는 푸셔 없는 구성입니다. 자동 분리·배출 푸셔는 구현 범위에 포함하지 않습니다. 래더에서 확인한 기대 동작, 통신 기록, 운영자의 실제 동작 관찰은 05 통합 테스트 결과서 8쪽에서 구분해 제시했습니다.

8. 검사 이력과 Web UI

SQLite에는 단순 PASS/FAIL만 저장하지 않고 검사 근거를 연결합니다.

예:

  • inspection ID
  • 촬영 시각
  • 원본 frame
  • 부품별 판정
  • reason code
  • 최종 판정
  • 모델·설정 정보
  • PLC cycle / event
  • 저장 상태

Web:

  • /line — 현재 라인 상태·최근 검사
  • /history — 검색·상세 조회·CSV 내보내기

화면의 몸체 정렬 0/3·분류 미실행 표시는 해당 이력의 오조립 참고 분석 상태입니다. 기본 결품 검사·최종 FAIL·원본 3장 저장과 구분해 읽습니다. 상세 구조와 예시는 06 DB 설명서 7~9쪽에 있습니다.

14. 성과 해석 기준

이 프로젝트는 교육용 엔진 모형을 대상으로 데이터 수집·라벨·학습·최적화·현장 검사·결과 추적을 연결한 구현입니다.

  • 개발 검증의 mAP와 실물 제품 PASS/FAIL은 서로 다른 평가 단위입니다.
  • 저장 사진의 모델별 처리시간과 3프레임 검사·저장·PLC 응답 전체 시간은 구분합니다.
  • 7건의 정상·결품 반복시험은 해당 조건의 구현 근거이며 장시간 신뢰성 인증이 아닙니다.
  • 통신 기록, 실물 관찰, 참고 분석과 최종판정은 각 기록의 의미를 유지합니다.

핵심 성과는 모델 검출에 그치지 않고, 검사에 사용한 원본과 판정 사유를 보존한 뒤 PLC에 전달하고 같은 ID로 다시 조회할 수 있게 만든 점입니다.
